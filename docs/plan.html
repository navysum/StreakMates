Product + technical plan · v3 · standalone app

Habits With Friends

A habit tracker where the streak isn't only yours. Private habits stay private — the ones you keep flaking on go in front of four people who will notice. A standalone app that borrows its look — the palette, the type and the component vocabulary — from the LifeOS portal, because that look is already right.

DM Sans + Cascadia Code Expo · React Native Supabase · Postgres 6 phases
01 · Core model

The one idea to get right

Everything else in this document falls out of this single decision.

Most habit trackers give each person their own private list. Yours has two kinds of habit, and the difference is one nullable column.

The core model

A private habit is a row owned by you with no group. A shared habit is one row owned by a group — and every member checks in against that same row. Nothing is copied per person. A table of check-ins keyed by (habit, person, date) does all the work.

That's why “The Gym Rats go to the gym 4× a week” can be one thing you all look at, rather than five separate habits that happen to share a name. When Maya taps her circle, she inserts a row for herself against the group's habit. The group board is just: for today's date, who has a row and who doesn't.

Once you see check-ins as facts about a person on a day rather than as state stored on the habit, the streak maths, the group board, the activity feed and the offline behaviour all get easy.

Separate app, borrowed look

This shares nothing with LifeOS but its appearance — separate codebase, separate database, separate account, separate everything. Copy the token values in once and they are yours to change freely; there is no sync to maintain and no dependency to break.

The rules the portal already follows, carried into the app unchanged: DM Sans for everything you read, Cascadia Code for every number, code and uppercase micro-label. Flat surfaces with a 1px border and an 8px radius — no shadows anywhere. Labels at 8px, 600 weight, uppercase, 0.06em tracking. Numerals always tabular-nums so columns line up. Rows divided by hairlines rather than gaps.

Already solved for you

The portal's HabitsCard settled the check-in circle: 18px, filled green when done, a 2px amber ring when not. That's the single most important control in the whole app, and it already exists in your system — the phone app inherits it rather than inventing one.

Both fonts are variable TTFs sitting in life-os-portal/fonts/. Copy those two files into the app and register them with expo-font — that is the entire extent of the relationship between the two projects.

One porting job

React Native has no CSS custom properties. Port variables.css once into a typed theme.ts that exports the same token names, and pick light or dark from the device setting. After that one copy, the file belongs to this app.

05 · Schema

How the data is shaped

Seven tables. If you understand these, you understand the app.

profiles

  • id uuid → auth user
  • display_name text
  • avatar_url text
  • timezone text
Created automatically the first time someone signs in with Google.

groups

  • id uuid
  • name text
  • emoji text
  • invite_code unique
  • created_by uuid
The invite code lives here and can be rotated by the owner.

group_members

  • group_id uuid
  • user_id uuid
  • role owner|member
  • joined_at timestamptz
Key is the pair, so nobody joins twice. This table decides who sees what.

habits

  • id uuid
  • owner_id uuid
  • group_id nullable
  • title, emoji, colour
  • cadence daily|weekly|days
  • target_days int[]
  • reminder_at time
  • sort_order int
  • created_at timestamptz
  • archived_at timestamptz
group_id null = private, set = shared. That column is the whole feature.

check_ins

  • id uuid
  • habit_id uuid
  • user_id uuid
  • local_date date
  • note text
  • created_at timestamptz
Unique on (habit, user, date). One tap per person per day, and safe to retry.

reactions

  • check_in_id uuid
  • user_id uuid
  • emoji text
🔥 and 👏 on a friend's check-in. One of each per person.

nudges

  • habit_id uuid
  • from_user uuid
  • to_user uuid
  • created_at timestamptz
Rate-limit to one per person per habit per day or friendships will suffer.

Streaks are calculated, not stored

Resist the urge to keep a streak number on the habit. A stored counter drifts the moment a check-in arrives late from an offline phone. Read the last N check-in dates and count backwards — it's fast for years of data, and it is always correct. Denormalise later only if a real screen gets slow.

06 · Invites

How the invite code works

Six characters, and one piece of server-side care that stops them being guessable at scale.

  1. Someone creates a group. The database generates a six-character code from an alphabet with no 0, O, 1 or I in it — about a billion combinations, none of which get misread across a pub table.
  2. They share it. The phone's share sheet sends “Join The Gym Rats: 7KQ2FM”, plus a deep link that pre-fills the code if the app is installed.
  3. A friend types the code. The app doesn't search the groups table — it calls one database function, join_group_with_code.
  4. That function runs with elevated rights and does three things: find the group, insert the membership, return the group. Because it's the only door in, ordinary users never get read access to the groups table, so nobody can scrape codes.
  5. They're in. Every shared habit appears in their Shared tab immediately, and the group sees “Sam joined” in Activity.
Guard rail

Rate-limit that function per user — around ten attempts an hour. Without it, a billion combinations is only a few days of brute force for a determined stranger. With it, it's forever.

07 · Permissions

Who can see what

The part most people get wrong, and the part that matters most when the app holds “No phone after 10pm”.

Postgres can enforce visibility in the database itself, so the phone app is never trusted to filter anything. Even someone poking the API directly gets back only their own rows.

TableWho can readWho can write
profilesYou, plus anyone sharing a group with youOnly your own
groupsMembers onlyThe owner
group_membersMembers of that groupYourself, to leave; the owner, to remove
habitsThe owner, or members of its groupThe owner; group habits, any member
check_insAnyone who can see the habitOnly rows where the user is you
reactions / nudgesGroup membersOnly as yourself
The trap everybody hits

Writing “you can read group_members if you're in group_members” makes Postgres check the rule to check the rule, forever, and every query dies with an infinite-recursion error. Fix it before you write a single policy: put the membership check in a small helper function marked security definer, and call that from every policy instead. One function, no recursion, and the rules stay one line each.

Private means private. A private habit has no group, and no policy anywhere grants another human read access to it. Make the choice explicit when a habit is created, and warn clearly before making an existing private habit shared — that can't be un-seen.

08 · Leaderboard

Ranking the group without wrecking it

A leaderboard is the fastest way to make a habit app fun, and the fastest way to make people quit it. The difference is entirely in what you measure.

No new tables

Every figure on these two screens is derived from check_ins — the same rows the group board already reads. If the leaderboard needed a new table, the core model would be wrong.

Rank consistency, not volume

Counting check-ins rewards whoever tracks the most habits. Someone with two habits they never miss would sit below someone with eight they half-do. Rank on completed ÷ expected instead, as a percentage, and the board is fair no matter how many habits each person carries.

“Expected” is the only genuinely fiddly part. For each person and each shared habit, count the days in the window where all of these hold: the habit existed and wasn't archived, the person had already joined the group, and the day matches the habit's cadence. Habits with a weekly target aren't per-day at all — those are completed ÷ (weeks × target). Getting this right is what stops someone who joined on Friday from appearing to have failed all week.

Privacy — non-negotiable

Only shared habits count toward any group figure. If private habits fed the percentage, the leaderboard would leak them: watch someone's score move on a day they logged nothing shared, and you've learned something they chose not to show you. The permission rules above already hide the rows; the maths has to respect them too.

Make last place survivable

Permanent last place is how people leave. Three things fix it, and all three are cheap:

  1. Rank a week, not all time. Everyone starts level on Monday, so one bad stretch isn't a permanent identity.
  2. Show most improved beside the ranking. A second way to win, and the only one available to the person at the bottom. Rae is third on the board and the best story on the screen.
  3. Put a collective number above the competitive one. The group streak — consecutive days where everyone hit at least one shared habit — makes the top of the screen something you win together before the part where you beat each other.

Rank people, diagnose habits

This is the line that keeps the feature kind. People get a rank and a percentage, and no one is ever labelled “worst”. Habits get judged bluntly, because a habit can't be offended and because the judgement is useful: a habit sitting at 29% across the whole group is a badly-set target, not four lazy people. That's the group's cue to move the time, lower the target, or drop it — so the “worst habit” tile should offer exactly those three buttons rather than just naming and shaming.

Guard rail — backfilling

If people can log any past date, the leaderboard is won by whoever backfills a month on Sunday night. But you can't simply ban late writes, because the offline queue legitimately sends yesterday's check-in today. The distinction is already in the table: local_date is the day it counts for, created_at is when it arrived. Let the offline queue write freely, and cap manual backdating at about three days with a check on the insert policy.

Where to compute it

Start on the phone. The group board already fetches this week's check-ins, so the weekly ranking is arithmetic on data you're holding — no new query, and it updates live with everything else. Move it to a group_leaderboard(group_id, since) database function when you want all-time figures or when a group gets big enough that pulling every row stops being sensible. Doing it in that order means the feature ships in Phase 4 and gets optimised only if it needs to be.

09 · Managing habits

Adding and removing has to be effortless

People abandon habit trackers because editing them is a chore. Adding one should take two taps and nothing but a name.

Adding

+ Add habit sits in the header of every habit list, so it's never more than one tap from wherever you are. The sheet asks for a name and nothing else — icon defaults to a neutral dot, colour to the palette green, cadence to daily, reminder to off, visibility to Private. Every field below the name is optional, and every one has a default that produces a usable habit. Sharing is always a deliberate act, never the default.

Removing — two different things

Almost everyone who wants a habit “gone” means stop showing it to me, not destroy the record. So there are two actions and the safe one is prominent:

ActionWhat happensWho can do it
ArchiveSets archived_at. Drops off Today, keeps every check-in, keeps the streak record, restorable in one tap.Owner; any member for a group habit
DeleteRemoves the habit and every check-in against it. Not reversible.Owner only
Group habits need a stronger guard

Deleting a shared habit destroys other people's history, not just yours. So only the group owner can delete one, and the confirmation has to say what is actually being lost — “this deletes 312 check-ins from 4 people” — rather than a generic “are you sure?”. Any member can archive a group habit for the whole group; that's recoverable, so it doesn't need the same ceremony.

The gestures

Swipe a row for Archive and Delete. Hold and drag to reorder — which needs a sort_order column on habits, cheap to add now and annoying to retrofit once people have twenty habits in an order they care about. Tap a row anywhere else to open its detail, and edit in the same sheet used to create it, so there's only one form to build and one to learn.

Rule of thumb

Adding is one tap and no decisions. Removing is one swipe with a recoverable default. If either ever needs a trip into Settings, it's built wrong.

10 · Pitfalls

Five things that will bite you

Every one is cheap to handle now and expensive to retrofit.

  • “Today” is not a server concept. Someone checking in at 11pm in Sydney and someone at 8am in London must land on their own dates. Work the date out on the phone from the user's timezone, send it as local_date, and never let the server derive the day from a timestamp.
  • The App Store will reject Google-only login. Offering a third-party sign-in obliges you to offer an equally private alternative. Sign in with Apple satisfies it and takes an afternoon. Build it before your first submission, not after your first rejection.
  • Taps happen underground and on planes. Write the check-in locally, show the filled green circle immediately, and queue the upload. The unique key on (habit, user, date) means a retry that arrives twice is harmless.
  • Nudges become harassment fast. One per person, per habit, per day, and a switch in settings to turn them off. Social pressure is the feature; being pestered is how the app gets deleted.
  • Leaving a group is a data question. Decide now whether Sam's history vanishes from the board or stays as a record. Keeping the rows but hiding the person is usually right, and it's much harder to add once people have left.
11 · Working without a laptop

Building this from an iPad and an iPhone

Entirely possible, and not a compromised version of the job — the whole toolchain for this stack already runs in the cloud. There is one decision to make early.

The short version

You direct the work from Safari, the code is written and pushed for you in a cloud session, the app is built by Expo's cloud builders, and the result lands on your phone. No Mac is involved at any point — not for development, not for the iOS build, not for submitting to the App Store.

Writing the code

This session is already the answer. GitHub Codespaces runs at github.com/features/codespaces in mobile Safari, works on the repository, commits and pushes without anything installed on your device. You describe what you want changed, review the pull request in GitHub's web interface, and the iPad never needs a terminal.

If you want to read or tweak files yourself, github.dev (press . on any GitHub repo) gives a full editor in Safari, and Working Copy is an excellent native git client for iPad if you prefer an app.

Seeing it run on your phone

This is the part with an actual decision in it, because of one Expo constraint: Expo Go — the free app that runs your project without building anything — can only run libraries Expo has bundled into it. Native Google Sign-In is not one of them. So you get a choice about when to leave Expo Go behind.

RouteWhat you getCost
Expo GoInstant preview of Phases 0–3 on your own iPhone. Use Supabase's browser-based Google login for now and switch to the native sheet later — a few lines' difference.Free
Development buildYour own app on your home screen with every native module working, updated over the air whenever code is pushed. Needed eventually regardless.Apple Developer, $99/yr

Recommendation: stay on Expo Go with browser-based login through Phase 3. It costs nothing, it needs no build step, and it gets you all the way to the group board — the point where the app is actually the product. Pay the $99 at Phase 4, when you want the native login sheet and push notifications anyway.

The loop, once you have a development build

Code is pushed, eas update publishes the new JavaScript to Expo's servers, and your phone picks it up next time you open the app — usually under a minute, over cellular, from anywhere. You are not tethered to a dev server on a machine at home, which is the thing that normally makes laptop-free development miserable.

Shipping it

EAS Build compiles the iOS app on Expo's Macs and EAS Submit uploads it to App Store Connect, which is itself perfectly usable in Safari on an iPad. Store screenshots can be captured on the phone. The $99 Apple fee and the $25 Google fee are the only hard requirements, and neither of them is a computer.

The one genuine limitation

Debugging is harder without a desktop — no side-by-side simulator, no browser devtools. It's manageable if the work stays in small, verifiable steps, which the phase plan already enforces. If you get properly stuck on something visual, that's the moment a laptop earns its place; everything else here does not need one.
